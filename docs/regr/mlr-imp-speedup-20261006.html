MLR：get_imp 提速策略与实测

发布于

2026年10月6日

本页属于 RegR 性能评估，评估对象是 MLR（pkgdown 站点）的 get_imp()。它在同一类树模型上算三种变量重要性：mean.SHAP、impurity 和 permutation（XGBoost 为 mean.SHAP、gain 和 permutation），各自归一化到 [0, 1] 后放在一起比较，并打印三张图。本轮优化只涉及默认的 ranger 后端。

主要结果

  • 同一会话里的生存调用 22.2 → 10.2 s，分类调用 14.1 → 6.8 s（WSL，SEER 甲状腺数据 seer_thyroid_mtc_2026 4387 行、7 个变量）。新会话的第一次生存调用 34.1 → 18.8 s。
  • 最大的一块是 TreeSHAP。600 行 SHAP 原来单进程算 9.0 s，改成按行分给多个进程后是 3.2 s，结果与单进程逐位相同。
  • Windows 上优化后的耗时与 Linux 接近：同一会话的生存调用 12.3 s、分类 7.3 s；新会话第一次生存调用 28.3 s，比 Linux 多出的部分来自加载包和启动工作进程，没有逐项拆开。
  • 剩下约 10 s 里仍有约 2.5 s 是白花的：本机没有装 shap 的 Python 环境，每次调用先启动 Python、失败后才回落到 TreeSHAP。
调用 WSL 优化前 WSL 优化后 Windows 优化后
生存，新会话第一次 34.1 s 18.8 s 28.3 s
生存，同一会话再调 22.2 s 10.2 s 12.3 s
分类 14.1 s 6.8 s 7.3 s
注记只有一项会改变数值

4 项里 3 项只改实现方式：多进程 TreeSHAP 与单进程逐位相同；不加载 mlr3verse 不影响模型；置换重要性换线程数后森林不变，只是重要性值的末位可能随线程数变化（以前样本量不同时线程数也会变，这一点并不新）。会改变数值的是第 4 项：没有 Python SHAP 时，生存分支的 mean.SHAP 改为解释 impurity 森林，不再另训一片同样设置的森林，差别相当于换一个随机种子。设了 set.seed() 时，同一会话里第一次与后续调用的结果仍然一致。

耗时都花在哪

优化前，一次生存调用（同一会话、第二次）约 20 s，分步实测如下：

环节 优化前 优化后 说明
尝试 Python SHAP（失败） 2.5 s 2.5 s 启动 Python 本身就要约 2.7 s，未改
impurity 森林（500 棵树） 1.5 s 1.5 s 未改
permutation 森林（500 棵树） 6.0–6.7 s 1.9 s 3 线程 → 16 线程
为 SHAP 另训的森林 1.9 s 0 改为解释 impurity 森林
unify（转换 500 棵树） 0.9 s 0.9 s 未改
TreeSHAP 600 行 9.0 s 3.2 s 单进程 → 多进程
三张图 1.0 s 1.0 s 未改

为什么 3000 行就要这么久：

  • SHAP 的计算量看的是树有多大，而不是样本量本身。TreeSHAP 的计算量大致是“解释行数 × 树数 × 每棵树叶子数 × 树深²”。生存森林叶子很小，3000 行训练出来平均每棵树约 200 片叶子，于是 600 行 × 500 棵树 × 200 片叶子，再乘树深的平方，单核要 9 秒。
  • 置换重要性对每个变量都要重算 C 指数。按 ranger 的实现，生存森林每棵树要在袋外样本（约 1100 例，37%）上算一次 C 指数，打乱 7 个变量后各再算一次；C 指数两两比较样本对，约 60 万对。合计约 500 × 8 × 60 万 ≈ 24 亿次比较，单线程 17 s。
  • 生存叶子要存整条累积风险曲线。这批数据有 285 个不同的随访时间，每片叶子都存一条 285 点的曲线，训练和 unify 都比同样大小的分类森林重得多（分类森林 4387 行训练 0.1 s，生存森林 3000 行要 1.5 s）。

优化策略

提交 策略 实测 结果
20e32fb 生存备用路径与分类路径的 TreeSHAP 改走 get_shp() 已有的分块多进程函数 600 行：9.0 → 3.2 s 逐位一致
86df983 生存置换重要性森林的线程数按“行数 × 变量数”定 3000 行 × 7 个变量：6.7 → 1.9 s 森林不变；重要性末位可能随线程数变
d0f9acc 只加载 mlr3proba + mlr3extralearners（生存）或 mlr3learners（分类），不加载整个 mlr3verse 新会话加载 5.5 → 1.6 s 一致；不再连带加载 torch
54d2fd6 没有 Python SHAP 时，生存 SHAP 解释 impurity 森林，不再另训一片 少训练一片森林，省 1.9 s 有变化：mean.SHAP 来自另一片同设置的森林

1. TreeSHAP 按行分给多个进程

TreeSHAP 对每一行单独计算，按行拆开再拼回来，结果与一次算完逐位相同。get_shp() 早已有这样的函数：先算 20 行估计剩余耗时，超过工作进程启动时间的两倍才开进程（最多 16 个、留出 2 个逻辑核；Windows 上按每个进程 4 s 启动时间估计）。get_imp() 的两个 ranger 分支此前直接调用单进程的 treeshap::treeshap()，现在改走同一个函数。这项改动同时去掉了 TreeSHAP 的进度条。

2. 置换重要性按工作量定线程

MLR 的自动线程数按每 1000 行 1 个线程来定，3000 行只给 3 个线程，而本机有 24 个逻辑核。置换重要性要对每个变量重新预测一遍袋外样本，工作量是“行数 × 变量数”，改用这个数后 3000 × 7 达到 16 个线程的上限：

线程数 1 3 8 16
耗时 17.2 s 6.7 s 3.0 s 1.9 s

impurity 森林的工作量只与行数有关，线程数不变。

3. 只加载需要的 mlr3 包

get_imp() 原来加载整个 mlr3verse 来注册 surv.ranger 和 classif.ranger。mlr3verse 会连带加载 mlr3torch 和 torch，新会话要 5.5 s；而 surv.ranger 由 mlr3extralearners 注册、classif.ranger 由 mlr3learners 注册，只加载它们需要 1.6 s。get_shp() 的生存路径之前已经做过同样的改动。

4. 复用 impurity 森林

生存分支原来建了三片森林：impurity、permutation，以及一片只在 SHAP 备用路径里训练的森林（500 棵树、不算重要性）。impurity 森林的树数、行数和线程数都与它相同，而重要性模式不影响 ranger 怎么长树，所以 SHAP 改为直接解释 impurity 森林。

内部抽样与样本量

get_imp() 内部只做一次性的不放回抽样，不做交叉验证或 bootstrap 式的重抽样，所以重要性没有不确定性估计，结果随种子变化。

路径 训练数据 SHAP 评估行
生存 未发生事件者与事件者之比超过 9:1 时，把前者抽到事件数的 9 倍；再超过 3000 行就随机截到 3000 600
分类 全部数据，不抽样 600

本例 3790:597 ≈ 6.3:1，没有触发 9:1 的调整，只是从 4387 行随机截到 3000 行。生存分支最多只用 3000 行，所以数据再大耗时也基本不变；分类分支不抽样，样本越多树越深，TreeSHAP 越慢。

尚未处理

下面几项要么改变结果，要么还没有做，留待以后决定：

  • 跳过注定失败的 Python 尝试（约 2.5 s）：没有可用的 shap 时可以直接走 TreeSHAP，不改变结果。也可以先 reticulate::use_condaenv("MLR-shap") 让它真正走 GPU，但那样 SHAP 会换成 get_shp() 的模型，数值会变。
  • SHAP 评估行数 600 → 300：TreeSHAP 4.4 s 对单进程 8.8 s，正好减半，但会改变结果。
  • 三种重要性不是同一个模型算的：Python 路径跑通时，SHAP 来自 get_shp() 的森林（200 棵树、最多 2000 行、单独抽样），impurity 与 permutation 来自另一份 3000 行的抽样（500 棵树）；分类分支也是三片各自训练的森林。这与帮助页“from one selected tree model”的说法不符。
  • 分类分支不抽样：TreeSHAP 的耗时随样本量大致线性增长，几万行时会明显变慢。

传入现成的 shp 时，ranger 路径完全跳过 SHAP 计算；这些说明也写进了 ?get_imp 的 Runtime 一节。

局限

  • 整次调用只跑了一次，机器负载会带来 ±1 s 左右的波动；前后差距远大于此。
  • Windows 只测了优化后，没有优化前的对照。
  • 只有一份数据、7 个变量。变量更多时置换重要性的工作量按变量数增长，多线程的收益会更大；SHAP 的耗时则主要取决于树的大小。
